# ADR-0018 · 작업 항목은 GitHub Issues에 두고 라벨은 두 축만 쓴다

```yaml
id: ADR-0018
status: accepted
statement: 이 저장소의 할 일과 버그는 GitHub Issues를 정본으로 삼는다. 라벨은 type과 area 두 축만 쓰고 진행 상태 라벨은 두지 않는다. 이슈는 버그·기능 두 템플릿으로만 열 수 있다.
confidence: 기록됨
source:
  - wiki/git.md 3절
  - .github/ISSUE_TEMPLATE/config.yml
```

## 맥락

결정 시점에 GitHub Issues는 **한 건도 열린 적이 없었다.** 라벨은 GitHub 기본값 9개가 손대지 않은 채 있었고, 거기에 `eas-build` 하나가 더 있었다(이건 분류가 아니라 EAS 빌드 트리거다).

작업 항목이 없었던 것은 아니다. 다른 곳에 흩어져 있었다 — 브랜치 이름(`zzzRYT/CHL-T1`), 계획 문서(`docs/plans/**`), 위키의 [`drift.md`](../drift.md) 확인필요 큐, 그리고 저장소 밖의 개인 볼트. 그래서 "지금 안 된 것이 무엇인가"에 한 곳에서 답할 수 없었다.

## 결정

**GitHub Issues를 이 저장소 작업 항목의 정본으로 삼는다.** 코드·PR·CI가 이미 여기 있고, `Closes #12` 한 줄로 이슈와 변경이 자동으로 묶인다. 저장소 밖 도구에는 이 연결이 없다.

라벨은 **`type:` 과 `area:` 두 축**만 두고, 값은 커밋 타입·scope와 **같은 단어**를 쓴다. 진행 상태 라벨은 두지 않는다.

## 대안

- **저장소 밖 볼트/트래커를 정본으로.** 기획과 우선순위를 코드 밖에서 다루기엔 낫다. 그러나 커밋·PR과 자동으로 이어지는 번호가 없어, 6개월 뒤 "이 변경이 무슨 문제를 고친 것인가"를 되짚을 수단이 사라진다. 개인 계획은 계속 밖에서 하되, **저장소가 책임지는 항목만** 이슈로 올린다.
- **Linear.** 워크스페이스는 있지만 회사 것이고, 이 앱을 위한 팀이 없다. 개인 앱 하나를 위해 회사 워크스페이스를 쓰지 않는다.
- **`status:` 라벨 축 추가.** 칸반처럼 보이지만 손으로 옮겨야 한다. 1인 저장소에서 잊히면 라벨이 사실과 어긋나고, 어긋난 라벨은 없는 라벨보다 나쁘다. 열림/닫힘 두 상태로 충분하다.
- **GitHub Projects 보드.** 자동화가 되지만 이슈가 0건인 상태에서 보드부터 만드는 것은 순서가 거꾸로다. 이슈가 쌓여 열림 목록이 안 읽히면 그때 연다.

## 귀결

- 기본 라벨 9개(`bug`·`enhancement`·`good first issue` 등)는 삭제했다. 이슈가 0건이라 잃은 데이터가 없다.
- 라벨 목록과 커밋 scope 목록이 **두 곳에 중복**된다([`git.md`](../git.md) 1·3절, 그리고 GitHub 라벨). 갈라질 수 있는 자리이고, 검사기가 잡아 주지 않는다. 새 영역을 만들 때 둘 다 고친다.
- 빈 이슈를 막았으므로 **템플릿 두 개에 맞지 않는 요청은 들어올 곳이 없다.** 그래서 템플릿 선택 화면에 메일·지원 문서 링크를 함께 둔다.
- 외부 기여자를 위한 `good first issue` 같은 안내 라벨이 사라졌다. 외부 기여를 받을 상황이 되면 다시 만든다.
