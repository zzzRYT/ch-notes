# Git 운용 규칙

이 저장소에서 **커밋·브랜치·PR·이슈·릴리스를 어떻게 다루는가.** 무엇을 만드는가는 [`policy/`](policy/index.md)·[`rules/`](rules/index.md)에 있고, 여기는 그것을 굴리는 방식이다.

각 규칙의 *이유*는 결정 기록에 있다 — 커밋 [`ADR-0016`](decisions/ADR-0016-commit-convention.md).

---

## 1. 커밋

### 형식

```text
<이모지> <타입>(<범위>): <제목>

<본문 — 무엇이 아니라 왜>

<트레일러>
```

예:

```text
🐛 fix(notes): 복원 경쟁 상황에서 최신 undo 유지

같은 노트를 연속으로 지우면 앞선 undo 타이머가 뒤 것을 덮어써
복원 대상이 어긋났다. 캡처한 노트 신원을 undo가 함께 들고 다니게 했다.

Refs #12
```

### 이모지 ↔ 타입 (1:1 고정)

이모지는 **타입에서 기계적으로 결정된다.** 고를 여지가 없다 — 고를 수 있으면 어긋난다.

| 이모지 | 타입 | 쓰는 때 |
|---|---|---|
| ✨ | `feat` | 사용자가 할 수 있는 일이 늘어남 |
| 🐛 | `fix` | 의도한 동작과 실제가 달랐던 것을 고침 |
| 📝 | `docs` | 문서·위키만 바뀜 (`wiki/`, `README.md`, `docs/`) |
| ♻️ | `refactor` | 동작은 그대로, 구조만 바뀜 |
| ✅ | `test` | 테스트만 더하거나 고침 |
| ⚡️ | `perf` | 측정 가능한 성능 개선 |
| 🔧 | `chore` | 빌드·의존성·설정·버전 bump 등 그 외 |
| 👷 | `ci` | `.github/workflows/**` |

이 표에 없는 타입·이모지는 쓰지 않는다. 표를 늘려야 하면 표를 먼저 고친다.

### 범위(scope)

선택이지만 웬만하면 적는다. 앱 모듈 이름 또는 운영 영역을 쓴다.

`notes` · `editor` · `bible` · `parser` · `db` · `share` · `settings` · `theme` · `list` · `workspace` · `search` · `ota` · `eas` · `release` · `deps` · `wiki`

두 영역에 걸치면 범위를 비우거나(`✨ feat: …`) 커밋을 나눈다. 범위 두 개를 쉼표로 잇지 않는다.

### 제목

- **한국어**로 쓴다. 타입·범위·트레일러는 영어 그대로다.
- **명사형으로 끝낸다** — "추가", "수정", "분리". "추가했다"·"추가함"은 쓰지 않는다.
- 마침표를 찍지 않는다. 50자 안쪽을 목표로 한다.
- 무엇을 바꿨는지 한 줄로 읽히게 쓴다. 이유는 본문에 쓴다.

### 본문

한 줄로 자명한 변경이면 생략한다. 그렇지 않으면 **왜 이 변경이 필요했는지**를 적는다. diff를 한국어로 옮긴 본문은 쓰지 않는다 — diff가 이미 그것을 말한다.

### 파괴적 변경

데이터 스키마, 공유 마크다운 포맷, 설정 파일 형식처럼 **이미 나간 앱의 데이터를 못 읽게 만드는 변경**은 반드시 표시한다.

```text
✨ feat(db)!: notes 스키마에서 body_text 컬럼 제거

BREAKING CHANGE: 1.0.x가 만든 DB는 이 버전에서 열리지 않는다. 마이그레이션은 …
```

타입 뒤 `!`와 `BREAKING CHANGE:` 푸터를 **둘 다** 쓴다. 하나만 쓰면 도구와 사람 중 한쪽이 놓친다.

### 트레일러

| 트레일러 | 쓰는 때 |
|---|---|
| `Refs #12` | 관련은 있지만 이 커밋으로 끝나지 않는 이슈 |
| `Closes #12` | 이 변경이 머지되면 닫히는 이슈 |
| `Co-Authored-By: … <…>` | 에이전트·공동 작업자 |
| `BREAKING CHANGE: …` | 위 참조 |

**`[skip ci]`는 쓰지 않는다.** 문서만 고친 커밋도 예외가 아니다. `main`의 OTA 발행이 CI 성공(`workflow_run`)에 매달려 있어, CI를 건너뛰면 **배포가 조용히 나가지 않는다**([`POL-RELEASE-001`](policy/POL-RELEASE.md)).

### 커밋을 나누는 단위

되돌릴 수 있는 가장 작은 단위 하나. 리팩터링과 기능 추가를 한 커밋에 담지 않는다 — 되돌릴 때 둘 중 하나만 되돌릴 수 없다. 동작을 바꿨으면 **관련 `RULE`/`CONTRACT` 수정을 같은 커밋에** 넣는다([`workflow.md`](workflow.md) 5단계).

## 2. Pull Request

`main`으로 가는 길은 PR 하나뿐이다. 직접 푸시는 GitHub 브랜치 보호가 막는다([`ADR-0017`](decisions/ADR-0017-pr-gate.md)).

### 병합 조건

| 조건 | 강제 |
|---|---|
| PR을 거쳤다 | GitHub 브랜치 보호 |
| CI(`Typecheck, lint & test`)가 통과했다 | GitHub 브랜치 보호 — 필수 상태 검사 |
| `main`의 최신 상태 위에서 검사가 돌았다 | GitHub 브랜치 보호 — strict |
| 리뷰 승인 | **요구하지 않는다** — 1인 저장소라 본인 PR을 본인이 승인할 수 없다 |
| 위키가 코드와 맞다 | 사람 — PR 템플릿 체크란 |

관리자도 우회하지 않는다(`enforce_admins`). 급할 때 뚫을 구멍을 남기면 급할 때 반드시 뚫게 되고, 그때가 정확히 검사가 가장 필요한 때다.

### 병합 방식

**merge commit을 쓴다.** squash·rebase 머지는 쓰지 않는다. 개별 커밋이 `main`에 그대로 남는 것이 [`ADR-0016`](decisions/ADR-0016-commit-convention.md)의 전제다.

그 대가로 **푸시 전에 브랜치를 정리한다** — `wip`·`오타 수정`·`리뷰 반영` 같은 커밋은 `git rebase -i`로 접어 넣는다. 되돌릴 수 있는 단위로 남길 커밋만 올린다.

### 제목과 설명

PR 제목은 커밋과 같은 형식으로 쓴다(`✨ feat(notes): …`). 커밋이 하나뿐인 PR은 그 커밋 제목을 그대로 쓴다.

설명은 [`PULL_REQUEST_TEMPLATE`](../.github/PULL_REQUEST_TEMPLATE.md)를 채운다. 세 칸뿐이다 — **무엇을·왜**, **검증**, **위키**. 검증 항목은 돌리지 않았으면 체크하지 않는다. 체크만 하고 안 돌리면 이 템플릿은 없는 것과 같다.

### 크기

한 PR에 목적 하나. 리팩터링과 기능 추가를 섞지 않는다. 리뷰어가 없더라도 **되돌릴 때 단위가 된다** — 이 저장소에서 PR은 리뷰 도구가 아니라 롤백 단위이자 CI 게이트다.

## 3. 이슈

**이 저장소의 작업 항목은 GitHub Issues에 산다**([`ADR-0018`](decisions/ADR-0018-issue-tracking.md)). 코드·PR·CI와 같은 곳에 두어 `Closes #12` 한 줄로 이어지게 하는 것이 목적이다.

### 무엇을 이슈로 만드는가

- 사용자에게 보이는 문제, 하기로 한 기능, 갚기로 한 부채 — **나중의 내가 다시 찾아야 하는 것.**
- 지금 바로 고쳐서 PR로 나가는 것은 이슈 없이 진행해도 된다. 이슈는 서식이 아니라 기억 장치다.
- 개인 일정·우선순위 메모는 여기 두지 않는다.

### 템플릿

빈 이슈는 막혀 있다. 둘 중 하나로 연다.

- **버그 신고** — 기대/실제, 재현 순서, 플랫폼이 필수다. 재현 순서 없는 버그는 몇 주 뒤에 아무도 못 고친다.
- **기능 제안** — **해결책이 아니라 문제**를 적는 칸이 먼저다.

그 외 문의는 템플릿 선택 화면의 링크로 메일·지원 문서를 안내한다.

### 라벨 — `type:` 과 `area:` 두 축

| 축 | 값 |
|---|---|
| `type:` | `bug` · `feat` · `docs` · `chore` — **커밋 타입과 같은 단어** |
| `area:` | `editor` · `bible` · `notes` · `db` · `share` · `settings` · `theme` · `workspace` · `search` · `ota` · `ci` · `wiki` — **커밋 scope와 같은 단어** |

`type:`은 템플릿이 자동으로 붙인다. `area:`는 손으로 붙인다. 없는 영역이면 라벨을 새로 만들되, **커밋 scope 목록과 같은 단어를 쓴다** — 두 목록이 갈라지면 둘 다 못 믿게 된다.

**진행 상태는 라벨로 관리하지 않는다.** 열려 있으면 안 된 것이고 닫혀 있으면 된 것이다. 그 사이를 손으로 옮기는 라벨은 1인 저장소에서 곧 거짓말이 된다.

`eas-build`는 사람이 분류하는 라벨이 아니다 — PR에 붙이면 EAS가 빌드를 만드는 동작 트리거다. 건드리지 않는다.

### 닫기

이슈는 **PR 병합으로 닫는다.** 커밋이나 PR 본문에 `Closes #12`를 적으면 GitHub이 닫는다. 손으로 닫을 때는 왜 닫는지 한 줄 남긴다 — "재현 안 됨"과 "안 하기로 함"은 다른 결말이고, 6개월 뒤에는 구분이 안 된다.
